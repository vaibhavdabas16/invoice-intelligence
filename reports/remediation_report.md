# Remediation report (v1 → final)

> **Superseded in part by phase 3 ([improvement_report.md](improvement_report.md)):** the
> "arithmetic arbitration" described in §2.3 no longer clears any disagreement automatically, because one
> automatic acceptance was measured to be wrong. The invoice-number check of §2.1 was generalised into
> value grounding of every field. Everything else below stands as recorded.

This phase took the failures found in [failure_analysis.md](failure_analysis.md) one by one,
investigated the cause, implemented a fix only where evidence supported one, and re-measured.
Two fixes were kept, one experiment was **removed** because it did not work, and several issues
remain open. All numbers come from files under `reports/experiments/`. The side-by-side table is
[experiments/v1_vs_v2.md](experiments/v1_vs_v2.md) (generated by `python scripts/compare_versions.py`).

Configurations compared:

| name | what it is |
|---|---|
| **v1** | the original submission: prompt v1, consistency re-read on scans, photos only downscaled, image-quality warnings trigger review |
| **v2** | intermediate: prompt v2 (+ `invoice_number_occurrences`), photo upscaling, arithmetic arbitration, invoice-number checks, image-quality warnings informational only |
| **final** | v2 **minus** the occurrences field (prompt v3 = v1 wording, byte-identical requests), PDF text-layer grounding kept |

## 2. Priority 1: known extraction failures

### 2.1 Invoice numbers (L10 `MAP/D/09-0312` → `MAP/09-0312`)

**Investigation.** In the mild-stress image the header value is legible: bold, about 7 px tall
at 843 px page width. The number is printed twice (header and footer) on all 9 labelled invoices.
The clean L10 (a scanned PDF) was always read correctly. Comparing the two code paths found the cause:
- **Scanned PDFs** are rendered so the page's long edge is 1568 px, which upsamples the embedded scan.
- **JPEG/PNG photos** were only ever downscaled, so a 1122 px photo reached the model with
  ~45% fewer pixels (972 vs 1,813 32-px patches). The model's vision encoder sees small glyphs
  such as `D/` in fewer patches.

**Fix 1: upscale image-only pages to the same 1568 px long edge (`UPSCALE_IMAGES=true`).**
Measured on mild stress, consistency check on (raw data: `stress_mild*`, `e1_*`, `v2_*`, `final_*`):

| | runs | L10 wrong | L02 wrong | L09 wrong | field errors / run |
|---|---|---|---|---|---|
| no upscaling (v1 + v2-without-upscaling runs) | 6 | **6/6** | 4/6 | 6/6 | 2.67 |
| upscaling (E1 + v2 + final runs) | 9 | **0/9** | 4/9 | 9/9 | 1.44 |

Clean documents are unaffected: the only labelled photo (L02, 1500 × 2070) is larger than
1568 px, and PDFs were already rendered at 1568 px, so their requests are byte-identical to v1.

**Experiment: repeated-printing cross-check (prompt v2), removed.** The model was asked to
transcribe each printing of the invoice number independently (header, footer, ...) so that code
could compare them. Result:
- **True positives: 0.** With upscaling off, L10 came back as `MAP/09-0312` at *both* header and
  footer in 2/2 runs, and the wrong L02 values were likewise copied into every occurrence. The model
  anchors on its first reading despite an explicit "do not copy" instruction.
- **False positives: 1.** In rot270, L10's main number was correct but the footer was misread as
  `MAP/D/09-312`.
- **Cost: +~150 output tokens per invoice** (U01: 234 → 389), the largest part of v2's
  12% cost increase.

It was first demoted to informational metadata and then removed entirely (prompt v3 = v1 wording).

**Fix 2 (kept): grounding against the PDF text layer** (`src/validation/identifiers.py`). For
digital PDFs, the extracted number must occur in the embedded text, ignoring only whitespace and
case. This is deterministic: a correct transcription cannot fail it, and any dropped or changed
character (`/D/`, separators, leading zeros) does. It costs no API call. Measured: 0 false positives on
the 12 digital-PDF invoices (6 labelled, 6 unlabelled). True positives cannot be measured,
because no digital PDF invoice number was ever extracted wrongly. Scans have no text layer, so for
them the independent re-read remains the identifier check. **No value is ever replaced.**

### 2.2 Line-item description (L09 `Pomfret` → `Parrot` / `Reefret`)

**Investigation.** At 2× zoom the word is readable to a human in the mild-stress image, but blur
plus JPEG q45 have merged the strokes of `om` and `f`. Without upscaling the row was wrong in 6/6 runs
(`Parrot` in 5, `Pomfret, white, kg` in 1). With upscaling it was `Reefret` in 9/9 runs, never `Pomfret`. Cause: the information was
damaged at the source by the degradation, and the model fills the gap with a word-like string.
It is not a preprocessing bug and not a schema or prompt issue.

**Outcome: not fixed.** No evidence-backed fix exists within this pipeline. Upscaling cannot
restore blurred strokes, and both reads now agree on the wrong word, so the re-read cannot catch
it either. It was flagged in 2 of the 9 upscaled runs (once by a re-read disagreement, once by
a model ambiguity note). Described in §6 as a known failure.

### 2.3 Disagreement resolution (U02)

**Investigation.** In v1, U02's first read (6 × 64.00 = 384.00) matched the image and reconciled
with the printed subtotal; the re-read (4 / 256.00) did not. The document was flagged for review
even though the arithmetic already showed which read was right.

**Fix: deterministic arithmetic arbitration** (`src/validation/consistency.py::arbitrate`).
Disagreements are typed as `text`, `numeric` or `structure`. A disagreement is resolved
without review **only if** all of these hold:
1. every disagreement is numeric (quantities, amounts, tax, total);
2. the first read passes *every* arithmetic check: totals, printed subtotal, tax lines, and
   quantity × unit price per row;
3. the re-read fails at least one of them.

In every other case the document is flagged: any text difference, both reads consistent
("insufficient evidence"), or only the re-read consistent ("values not swapped automatically").
Values are never taken from the re-read.

**Measured in real runs:**
- v2 batch, U02: the re-read misread line 4 as 96.00 instead of 98.00 and failed its totals
  check; the first read passed everything. **Resolved automatically**, not flagged. The output
  matched v1 and the image.
- Final batch, U02: this time the *first* read misread line 4 as 9.60 / 96.00. That is consistent
  within the row but breaks the subtotal (829.75 vs printed 831.75). The repair call returned the same
  misread. The re-read (98.00) passed every check. Arbitration returned *"only the re-read is
  arithmetically consistent; values not swapped automatically"*, so the document was
  **flagged**, with both values shown in the review reason.
- In the stress-set runs, no disagreement was purely numeric, so arbitration never applied
  there (every disagreement involved a text field and was correctly left to review).

## 3. Priority 2: rotated scans (U05)

**Investigation, on a test bed of 40 pages × 4 rotations = 160 cases with known orientation**
(all 20 originals except U05, plus 20 stress images):

| question | best heuristic | result |
|---|---|---|
| is the page turned 90°? | row/column text-line profile ratio (already in v1) | threshold 0.6: 2/78 false warnings, 6/78 misses. All errors are photos with a textured desk background (L02, U02 family); perfect on scans and PDF renders |
| which way (90° vs 270°)? | ink-centroid position | **89.7%** correct (typographic line-asymmetry: 59%) |

At 89.7% direction accuracy, auto-rotation would turn about 1 in 10 rotated pages upside down.
That damages documents, so **auto-correction was not implemented**. The more important finding is
that it is not needed. On the rotated stress sets (labelled documents turned 90° and 270°, GT
unchanged), the model read **all 9 single-page documents fully correctly in both directions
(18/18)**, in v1, v2 and final. The only errors are on L04, which is an artifact of how I built
the test set: two pages stacked and turned sideways into one 1568 × 554 image, so each page is
tiny. That shows resolution limits, not rotation limits.

Before vs after on U05: the extracted JSON is unchanged (identical to v1); the review flag
went from "flagged for rotation only" to "not flagged"; both reads agree.

## 4. Priority 3: image-quality warnings

| signal | evidence | decision |
|---|---|---|
| low contrast | flagged L05/L07 in every mild run (8 flags), all on correctly extracted documents; the documents with errors had contrast 57, 21 and 30, the flagged correct ones 18.5 and 16.9 | removed as review trigger |
| low sharpness (Laplacian) | inverted on noisy images: severe-stress pages score 17–31, *above* mild pages (10–24), because noise produces strong edges | removed as review trigger |
| possible 90° rotation | flagged all rotated test documents (18 false flags, 0 errors on single pages) | removed as review trigger; kept as a prompt hint (free) and as metadata |
| blank / tiny page | rejects unusable input before an API call; covered by tests | **kept** (this is input validation, not a soft warning) |

No replacement quality score was added. The signals that do predict errors are already in the
pipeline: the model's own `illegible_fields` (100% recall on severe stress) and the independent
re-read. A resolution threshold would separate severe from mild stress, but those documents were
already all flagged by `illegible_fields`, so it would add nothing measurable.

## 5. Priority 4: failure handling (mocked, no API spend)

`tests/test_failure_handling.py` (20 tests) drives `process_document` → extractor → retry loop →
**the real `OpenAIProvider`** → a fake SDK client, so error mapping, retries, repair and review
are exercised together:

| scenario | verified |
|---|---|
| HTTP 429 | retried; exponential backoff `[1.0, 2.0]` s (jitter pinned); `Retry-After: 20` honoured; `insufficient_quota` 429 **not** retried |
| HTTP 500 | retried then succeeds; exhaustion stops after `max_retries + 1` calls with no repair calls |
| API timeout | retried; exhaustion: exactly 4 calls, sleeps `[1, 2, 4]`, category `provider_timeout`, "gave up after 4 attempts", error hint, `needs_review`, $0 cost, explicit error object instead of a fake `is_invoice:false` |
| auth error | 1 call, no sleep, `provider_auth` |
| malformed JSON | one repair call; a second failure stops (no third call), `extraction_parse_error`, both failed responses' cost reported |
| invalid schema / missing fields | repaired, or failed with `schema_validation_error` naming the fields |
| financial mismatch | one repair max; persistent mismatch keeps the printed value and flags "totals do not reconcile" |
| repair call hits provider errors | the valid first answer is kept and flagged |
| truncated output (`max_output_tokens`) | treated as a parse failure and repaired |
| duplicate calls | digital PDF = 1 call; non-invoice scan = 1 call (no re-read); bad input = 0 calls; cache = 1 call for 3 runs |

**Mutation check:** loosening the retry bound by one (`attempt >= max_retries + 1`) made 5 tests
fail (3 new, 2 existing). The tests detect an off-by-one in the retry limit. The code was restored.

**First real repair.** The repair path fired once in real use (final batch, U02) and
**did not fix** the error: it returned the same misread. That is 0/1, too little to judge, but it
is the only real evidence there is.

## 6. Remaining limitations and known failures

**Silent errors on degraded scans (most important).**
- L09 `Pomfret` → `Reefret` is wrong in every run and usually unflagged.
- L02's invoice number is still misread in 4/9 upscaled runs and caught in 1 of them.
- Mean silent errors per mild run: 1.33 (v1) → 1.00 (final).

There is a trade-off here. Upscaling removed most of the *uncertain* errors (which the re-read
used to catch), so the remaining errors are more consistent between reads and flag recall fell
(56% → 40%) even though there are fewer errors overall. Pooled over every run with the re-read on,
silent errors are 0.8 per run without upscaling (5 runs) vs 1.0 with it (6 runs). That difference is
within noise. **Upscaling reduces wrong outputs; it does not reduce silent errors.**

**U02's final output contains a misread** (line 4: 96.00, where the image shows 98.00). It is flagged,
and the review reason shows the re-read's 98.00. The output was not hand-corrected or regenerated:
it is what the pipeline produced.

**False-positive behaviour.**
- Final review flags on correct documents: 0 on clean, 0 on mild stress, 0 on rotated sets.
- In the v2 runs the re-read raised 2 false flags on correct documents across 6 stress runs
  (L02's re-read misread the number as `SGS/24847` and `SGSI/1847`). This is the inherent cost of
  the re-read. The final runs happened to have none.

**Not measurable on this data:**
- the true-positive rate of text-layer grounding (no digital PDF invoice number was ever wrong);
- the repair loop (one real firing, unsuccessful);
- arbitration on a labelled document (it only arose on unlabelled U02).

**Small samples.** Stress-set comparisons use 3 runs per configuration, and the severe/rotated
sets one run each.

## 7. Proposed future improvements (not implemented, not measured)

1. **Accept a fully consistent re-read when the first read is inconsistent.** It would have fixed
   U02 in the final batch, but it means trusting the second read on arithmetic evidence alone. Its
   error rate is unmeasured, so it is left for a labelled set with real disagreements.
2. **High-resolution crops** of the header and item table for scans. This targets L02/L09-type
   misreads at the source, at about +2k input tokens per scan.
3. **A harder labelled set** of real phone photos. The clean set still cannot separate any of the
   configurations.
4. Matcher: treat `L.L.P.` and `LLP` as equal (failure analysis §D). This needs to be pre-registered,
   not changed after seeing results.
